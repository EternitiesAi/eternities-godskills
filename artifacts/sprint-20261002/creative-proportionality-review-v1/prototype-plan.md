# Compact planning output — settled-platform creative prototype

Status: **planning only; no rendered build or acceptance observed.**
Context: the same exploratory one-screen brief used by the source-fit sidecar.
Desktop Chromium, 1280 x 800 baseline; pointer click and Space. No mobile,
VR, gamepad, score, failure state or commercial feature is requested.

Build the smallest viewable interaction: a pulse changes the surrounding field
and invites another exploration. As one optional direction, it can briefly gather
drifting forms before releasing them; the artist remains free to choose imagery,
palette, renderer, typography, composition, rhythm and interpretation. Do not
turn that suggestion into an aesthetic acceptance threshold. Keep the slice
self-contained and local; no network-dependent or asynchronously loaded assets
are needed for this proposed first slice.

Muse owns visual direction and the viewing brief; Arcadia owns the legible
pulse-to-world interaction and applicable browser lifecycle checks. Do not
manufacture a storyboard, media workflow or full release matrix.

One surface is initialized once per page in this proposed slice. In-app scene
replacement/remount and asynchronous asset completion are absent *by this
declared design*, not waived despite being required. If implementation adds
repeated setup, framework remounts, async assets or borrowed resources, their
lifetime, late-settlement, duplicate-loop and ownership checks become required.
Record an absent required guard as a gap, not "not applicable."

For the actual browser interaction, plan checks for pointer and Space operation,
focus/held-input recovery, visibility/long resume without applying a giant time
step, actual-container resizing and pointer mapping, one scheduling owner, and
owned-work cleanup on the supported lifetime. Include a suitable reduced-motion
presentation where applicable; no accessibility or device-wide certification is
claimed. These checks remain pending until a runnable build exists.

Next: implement the authorized prototype, then the requester or designated
creative approver directly views and operates it in the target browser. Record
the build/context, accepting person's actual identity, their judgment, visible
operability issues and remaining limits. The approver is not yet named and no
result is recorded. A screenshot, mock or checklist cannot substitute for that
viewing. Acceptance of an exploratory artifact is not formal release or measured
performance. No implementation or rendering is performed by this review.
