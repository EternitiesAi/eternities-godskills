## Completeness and consistency

Outcome: determine whether a bounded deliverable fulfills its declared obligations, identify substantive omissions and contradictions, and give a useful repair path with honest coverage.

Inputs: governing request/contracts, requirement standing, intended audience, artifact inventory/revisions, dependency boundaries, evidence access, finite audit budget, and audit-only or repair authority. Missing governing material limits scope rather than authorizing acquisition.

Operations: decompose independently failing requirements; locate actual details; separate content, semantic agreement and support; trace producer/transformation/consumer edges; choose distinguishing counterexamples; challenge inventory coverage and redundant detail; prioritize coherent repair; reopen changed obligations and dependents.

Outputs: obligation map with origin and exact artifact locations, material dependency/conflict record, distinguishing checks and observations or skips, repair/check/owner, declared counts if useful, exclusions and unknown coverage. Success evidence is retrievable content and checks appropriate to the requested evidence level, not a topic mention or longer output.

Effects: artifact reads; an audit report; only repairs already authorized at exact targets. No acquisition, installation, publication or new acceptance requirements are implied.

Positive triggers: multi-artifact requirement coverage; a deliverable that appears thorough but misses details; inconsistent contracts, implementation, tests or documentation. Negative triggers: isolated spelling correction, simple style change, output length without a coverage problem.

Dependencies: supplied or host-accessible artifacts and the ordinary ability to inspect them. Execution is conditional on available, authorized checks. Related Forge/Architect/Phoenix methods are optional; no tool or service is required.

Failures: conflicting requirements, missing artifact, unknown runtime behavior, uninspected upstream boundary, incomplete scope inventory, repair without authority, or audit budget exhaustion. Preserve the exact held conclusion and smallest resolving fact rather than inventing coverage.

Termination: all declared obligations receive supported dispositions and material dependencies agree, or named access/decision/evidence/budget boundaries prevent further inspection. Complete audit reporting is distinguishable from accepted delivery.

## Long-horizon work

Outcome: keep a finite authorized objective actionable across milestones and interruption, reconcile current state, and finish only at actual acceptance/effect gates.

Inputs: objective/finish condition, invariants, exact targets/effects/owners, milestone dependencies, current sources/revisions, live resource allowance, pause/stop steering, host facilities, receipts and any permitted continuity packet.

Operations: establish a scoped work contract; choose ready milestones; inspect live ownership; record consequential intent/identity before dispatch where storage exists; checkpoint decisions and evidence; resume by identity/authority/source/ownership reconciliation; hold unknown effects before retry/cancel/compensate; execute the next permitted action; close or hand off honestly.

Outputs: compact continuity packet, milestone status and invalidation reasons, effect ledger, observed checks, active/paused/blocked/complete state, next action and owner. Success evidence attaches to actual candidate/effect identities and current prerequisites.

Effects: currently authorized local or external work only. The guide neither starts a worker nor provisions storage/scheduling. Checkpoints preserve authorization without enlarging scope, cost, access or consequences.

Positive triggers: sustained objective across sessions; interruption near an external effect; stale branch or changed owner invalidating a checkpoint. Negative triggers: one-step work, ordinary status lookup, requesting scheduler implementation or guaranteed unattended execution.

Dependencies: active execution for progress; approved state retention for durable recovery; authoritative effect observations or a real deduplication contract for uncertain mutations. A runner/wake mechanism is needed only if scheduled continuation is requested and already authorized. Portable fallback returns a user-retained packet and resumes only when the host is active. Missing facilities are explicit.

Failures: stale source, contested ownership, missing/corrupt packet, unknown paid result, partial external success, resource exhaustion, changed authority or scoped pause. Hold only the dependent action and preserve safe independent work.

Termination: actual objective evidence and required integration/effect gates are met, or a demonstrated boundary requires handoff. A packet or plan does not complete an execution task. No claim of uninterrupted or multi-day performance.

## Source comparison and selection

| Existing source capability | Useful mechanism | Candidate's additional decision work | Excluded import |
| --- | --- | --- | --- |
| Forge: multi-phase delivery | Slice evidence, disjoint ownership, bounded closure, retain authorization | Obligation standing and finite coverage; live milestone reconciliation | Model-feedback execution or mandatory delegation |
| Architect: system decision/contract propagation | Producer-consumer semantics and whole declared inventory | Separate presence/agreement/support, inventory challenge, nonredundant detail | Full architecture redesign for a small audit |
| Mnemosyne: continuity/context/retrieval | Minimal source-labeled state, freshness and explicit unknown | Resume against live owners, resource/pause state and milestone invalidation | Repository collection lifecycle, global memory policy, identity store |
| Phoenix: diagnosis/recovery | Negative evidence, exact target/effect proof, reconcile before retry | Continuity branch for uncertain effect and unaffected permitted work | Private interaction mining or diagnosis ritual without a failure |
| Hermes: integration workflows | Operation identity, real retry semantics, partial-success receipts | Portable no-runner fallback and paused/active distinctions | API adapter, executor, stream parser, required vendor/tool |

The comparison is a design rationale against exact inspected bodies, not an experiment or quality ranking. Full source pins and license uncertainties are in `source-ledger.json`. Fresh prose and templates were authored from the approved contract; no source body was copied into the product.

## Progressive disclosure

Each entrypoint carries its complete essential decision procedure. Completeness loads its table template for multiple obligations and worked audits only for concrete tracing guidance. Long-horizon loads the packet for handoff, effect recovery only for ambiguity, and interruption cases only when examples help. Metadata relationships suggest companions without importing or requiring them. References use only links inside the portable skill tree.

The product trees include no executable workflow, native adapter, required model, proprietary API, scheduler, global memory hook, or workstation path. The sidecar checker is a local read-only authoring check and is not bundled as a runtime dependency.
