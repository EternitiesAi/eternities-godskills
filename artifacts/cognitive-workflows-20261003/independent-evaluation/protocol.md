# Independent application protocol v1

Preregistered before reading any of the six candidate bodies. The evaluator is
a non-author. The evaluator also constructed these cases and criteria: this is
not an expectation-blind assessor, a fresh-model trial, or a matched comparison.

## Contract and scope

Outcome: determine whether each exact frozen method provides usable guidance for
its declared outcome and whether applying it to an independent concrete case
produces the requested artifact within existing authority. Inputs are the frozen
candidate bytes, bundled references needed for that case, the raw case, and the
read prerequisites recorded in `sources.json`. Outputs in the later pass are
instruction-review findings, actual application artifacts, criterion evidence,
unresolved limits, and a bounded disposition for each method.

Operations: verify identity; review instructions; apply to raw input; preserve
output; assess against the separate preregistered criteria. Effects are local
reads and evaluator artifacts only. Finish when all six have evidence and a
disposition, or a specific identity/access problem prevents an affected case.
This initial task finishes with preregistration and stops before those operations.

| Raw input | Method outcome |
| --- | --- |
| C01 | Inspectable voice profile and a factually faithful rewrite |
| C02 | Different concepts and a feasible developed fictional experience |
| C03 | Evidence-aware interpretation and respectful usable dialogue |
| C04 | Recovery and minimal retention of conflicting, uncertain task state |
| C05 | Obligation-to-artifact audit with omissions and contradictions |
| C06 | Resumed useful work preserving authority and uncertain-effect handling |

Do not force these methods onto greetings, simple rewrites, routine edits, or
tasks outside their scope. Raw cases contain paraphrased user requests rather
than expected answers. This application exercise does not test catalog discovery;
the parent owns real catalog direct/paraphrase/adjacent checks and integration.

No descendants, providers/APIs, network acquisitions, private data, warehouse
scans, installation, commits, product/shared generated-file writes, protected
activation/R10 changes, or global instructions/memory writes. All write targets
stay under this independent-evaluation directory. Fixture instructions authorize
only simulated task decisions and local evaluation artifacts, never real external
actions. Do not execute fixture snippets or treat fictional receipts as live jobs.

## Freeze and leakage handling

1. Bind this protocol, six raw files, criteria, and supporting records using the
   SHA-256 manifest. Verify it before application. Do not replace preregistered
   criteria after seeing an output. Record necessary amendments in separate
   versioned files with timing, reason, old/new identities, and affected claims.
2. Keep raw inputs and assessor criteria evaluator-only until authors freeze
   their trees. Authors must not receive expected answers. Separation is a
   procedural control; absent access logs, say that access was not technically
   excluded. Record any known leakage. Repair feedback may identify a defect,
   but fixes and reruns on these disclosed cases are no longer held-out evidence.
3. Parent supplies exact worktree-relative paths and a per-file SHA-256 inventory
   for every frozen candidate tree, including its metadata and bundled resources.
   Verify the inventory against the actual files and reject unexpected/missing
   files or mismatches. If only an aggregate is supplied, require its canonical
   encoding and verify it; do not invent one or infer readiness from author status.
   Do not review an unfinished or unfrozen tree. Draft metadata awaiting independent
   review is an expected process state, not a substantive instruction defect.
4. Read a locally supplied Skill Creator instruction fully before this next pass.
   Record its path/hash and read completion in a supplemental receipt; preserve
   this v1 preregistration unchanged. If it changes the protocol materially,
   preregister the amendment before reading candidates. Do not claim this
   prerequisite has already been satisfied.

## Later review/application sequence

1. Create a unique `applications/<run-id>/` under this directory only after parent
   requests the next pass. Preserve candidate hash verification and leakage facts.
2. Review each selected complete entrypoint and only required bundled references.
   For each, check applicability/exclusions, usable inputs, decision procedure,
   outputs, recovery, finish conditions, and host portability/authority. Cite
   exact paths, hashes and line anchors for findings. Source-history paths need
   not exist on a receiving host; executable dependencies actually required do.
3. Apply C01 through C06 in order, using only the corresponding frozen method and
   raw case unless the method requires an explicitly bundled reference. Do not
   substitute an expected-answer checklist for using its procedure. Record which
   mechanisms actually affected the output and any unsupported or unavailable
   step. First preserve `Cxx/output.md` verbatim; then perform assessment. No
   provider calls or additional agents are permitted. Shared context and evaluator
   familiarity limit independence; disclose them, rather than claim a blind run.
4. C04 permits a real local fixture note and readback inside its own application
   directory. Compare recovered content with the saved note and the supplied
   evidence. That demonstrates only this file-backed retention/recovery, not
   unaided recall, cold-session recovery, unlimited memory, or global store writes.
   If persistence cannot be exercised, record the proposed content and that limit.
5. Assess each criterion as supported, violated, or unresolved, with output
   quotations/anchors and source evidence. Check exact user constraints directly
   where practical. Assess aesthetic coherence/originality as reasoned subjective
   judgment with plausible alternatives, not a unique target or numeric score.
6. Separate a defective instruction, an application error, a host limitation,
   and missing evidence. Do not attribute every weak answer to the method. Give
   each real defect its trigger, consequence, evidence, and the smallest coherent
   repair suggestion; this evaluator does not edit author-owned bodies.
7. Finish with a per-method disposition: acceptable for the bounded case,
   repair needed, or unresolved with the precise reason. Any critical outcome or
   authority violation prevents an acceptable disposition. Material omissions
   also require repair. Unmeasured qualities remain unmeasured. Preserve initial
   failures and exact rerun identities; do not erase them after repair.

## Claims and limits

There is one deliberately demanding case per method, not a representative
benchmark. No ungrounded quality score, universal superiority, promotion,
deployment, installation, diagnosis, consciousness, runtime scheduling, or
complete source-refinement claim follows. A method may be useful without being
better than ordinary competence. No baseline is run or assumed in this task.
Formatting/integrity checks qualify identities and records, not instruction
quality. Parent-owned package, discovery, export and release gates remain separate.
